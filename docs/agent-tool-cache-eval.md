# 工具结果共享缓存 A/B 评测

## 结论

通过 A/B 评测证明:接入工具结果共享缓存后,**后端工具调用降低 35.9%**,**单次重复工具调用耗时降低 99.8%**。

| 指标 | 关闭缓存(对照组) | 开启缓存(实验组) |
| --- | --- | --- |
| 第 1 遍工具真实执行次数 | 98 | 92 |
| 第 2 遍工具真实执行次数 | 101 | **59** |
| 后端调用变化 | +3.1%(无下降) | **−35.9%** |
| 第 2 遍共享缓存命中率 | 0.0% | **43.2%** |
| 端到端 P50 | 9210 → 8772 ms(−4.8%) | 8611 → 8088 ms(−6.1%) |
| 端到端 P95 | 10480 → 9611 ms(−8.3%) | 10304 → 9800 ms(−4.9%) |

受控重复调用(同一工具、同一参数连续两次):

| 工具 | 第一次(真实执行) | 第二次(共享缓存命中) | 节省 |
| --- | --- | --- | --- |
| search_knowledge_base | 3900 ms | 4 ms | 99.9% |
| search_knowledge_base | 396 ms | 3 ms | 99.2% |
| search_poi | 497 ms | 1 ms | 99.8% |
| 合计 | 4793 ms | 8 ms | **99.8%** |

## 实现要点

- 缓存介质:Redis(`AgentToolResultCacheService`),TTL 300s,key = `SHA-256(工具名 + 规范化参数)`;
- 双层缓存:执行内 memo(`tool_result_reused`,防止同一轮内重复调用)+ 跨请求共享缓存(`tool_result_shared_cache_hit`);
- 只对同时声明 `supportsIdempotentReplay()` 与 `supportsSharedResultCache()` 的**幂等只读工具**启用(知识库检索 / POI / 附近 POI / 社区攻略 / 路线详情),`todolist` 等有状态工具不缓存;
- 容错:Redis 读写全部 try-catch,异常时自动降级为"无缓存",不影响主链路;
- 开关:`liuliu.redis.agent-tool-cache.enabled`(默认 false)。

## 评测方法

- 用例:20 条标注用例(知识库检索 / 地图 POI / 路线详情 / 别名简称 / 多约束 / 闲聊),取自 `backend/src/test/resources/agent-eval-cases.json`;
- 每种模式跑 2 遍:第 1 遍冷启动填充缓存,第 2 遍观察缓存效果;
- 对照组与实验组使用同一批用例,唯一变量是缓存开关;
- 真实调用大模型(deepseek-chat)与全部工具,统计"工具真实执行次数"与"端到端耗时"。

复现命令:

```powershell
$env:AGENT_BATCH_EVAL='true'; $env:AGENT_BATCH_PASSES='2'; $env:AGENT_BATCH_LIMIT='20'
$env:AGENT_BATCH_CACHE='true'   # 对照组改为 false
mvn test -Dtest=AgentBatchEvaluationTest
```

报告产物:`backend/target/agent-batch-cache-report.md`、`backend/target/agent-batch-nocache-report.md`。

## 局限与说明

- 热启动缓存命中率为 43.2% 而非 100%:大模型每次生成的工具参数存在细微差异,参数不一致即为不同 key;提高命中率需要约束参数写法或做参数归一化;
- **端到端耗时收益有限(约 6%)**:单次请求约 8 秒,主要由大模型推理(4~6 轮)构成,工具耗时占比不高,因此缓存主要收益在"减少后端调用与外部配额消耗",而非端到端延迟;
- 对照组同样出现约 5% 的耗时波动,说明该量级属于模型生成噪声,不能归因于优化,故以对照组作为噪声基线;
- 知识库更新后缓存最多陈旧一个 TTL(300s),目前依赖 TTL 过期,未做主动失效。

## 缓存命中 ≠ 模型在重复调用工具

缓存的命中要区分两类,否则很容易被误读成"模型在乱调工具":

| 命中类型 | 含义 | 对应返回码 | 实测数据 |
| --- | --- | --- | --- |
| **执行内重复** | 同一次会话里,模型用相同参数又调了一次同一个工具,被执行内 memo 拦截 | `tool_result_reused` | 30 条用例、161 次调用中 **0 次**(未出现同参数重复调用) |
| **跨请求复用** | 不同请求(或重跑同一批请求)命中同一条查询,由 Redis 共享缓存返回 | `tool_result_shared_cache_hit` | 重跑 20 条用例,第 2 遍 **57/132 = 43.2%** |

结论:

- 43.2% 是在"同一批用例重跑第二遍"的受控实验下测得的,反映的是**查询在请求之间的重复度**(热点地点被反复检索),**不代表单次会话里模型乱调工具**;
- 真正衡量"模型重复调用"的指标(执行内同参数重复)实测为 **0 次**,说明模型在单次会话内并没有反复调用同一个工具;
- 需要说明:评测早期曾把 `deterministic_prefetch`(**预取结果标记**,不是错误码)误统计成"工具失败/重复调用",据此得出过"11 次工具失败""14 次执行内重复"的错误结论,现已修正;
- 因此缓存的收益是:即使模型重复调用,也不会产生重复的后端/外部 API 调用。

## 如何防止模型重复调用工具

| 优先级 | 手段 | 状态 |
| --- | --- | --- |
| 1 | **工具结果回填**:每次执行后把结果(经 `AgentToolResultSlicerService` 切片)写回消息上下文,让模型"看得见"已有信息 | 已实现 |
| 2 | **Prompt 约束**:`PIPELINE_GUIDE` 中要求"Avoid repeated overlapping tool calls when existing results already answer the question" | 已实现,可强化为"调用前先检查已有工具结果" |
| 3 | **失败引导**:工具失败 payload 带 `fallbackSuggestion`,明确"不要用相同参数重试,基于已有信息作答" | 已实现 |
| 4 | **工具描述与参数规范化**:写清工具能返回什么、参数语义,并统一地名等参数格式,减少"换个说法再试" | 待优化 |
| 5 | **兜底去重**:执行内 memo + Redis 共享缓存双层拦截,重复调用不产生后端请求 | 已实现 |
| 6 | **轮次预算与收敛提示**:接近 6 轮上限时提示模型收敛作答 | 待优化 |

## 面试问答:命中率高是不是说明模型重复调用?

> 这里要区分两种重复:**执行内重复**和**跨请求重复**。
> 我们用数据把两者分开了:30 条用例、161 次工具调用中,执行内同参数重复是 **0 次**——模型在单次会话里并没有反复调同一个工具;而重跑同一批用例时第 2 遍命中率 43.2%,那属于**跨请求复用**,说明这些查询在请求之间本身重复(热点地点),这正是共享缓存的价值,不是模型在乱调工具。
> 防止模型重复调用,我们做了三层:第一层是结果回填,每次工具结果都写回上下文,让模型看得见已有信息;第二层是 prompt 约束,明确要求"已有结果能回答就不要重复调用";第三层是去重兜底,memo + Redis 双层缓存,即使模型重复也不产生后端调用。这三种手段的有效性我们用"执行内重复调用率"作为回归指标持续监控。

如果被追问"那工具失败率是多少":

> 修正统计口径后,30 条用例的**真实工具失败率是 0%**(161 次调用全部正常返回)。早期版本曾报出 6.6%,是因为把 `deterministic_prefetch`(预取结果标记)误判成了错误码——这类"指标口径错误"本身也是评测里必须警惕的问题,我们是通过把失败明细(工具名 + 返回码)记录下来才定位到的。
> 另外我们顺手加固了 `nearby_pois`:它的 schema 原本把 `lat/lng` 声明为必填,而模型在规划阶段通常拿不到坐标,存在参数校验失败的风险;现在支持传地名,由服务端先做地理编码(高德 `/v3/geocode/geo`)再查周边,坐标与地名两种入参都能正常工作。
